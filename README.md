<p align="left">Digital Wallet Transaction System<br>Overview<br>Build a simple digital wallet system demonstrating PostgreSQL and Kafka integration. Users create wallets, add funds, and transfer money. Transaction history uses Kafka events for eventual consistency.<br>What You'll Learn<br>	•	PostgreSQL transactions<br>	•	Kafka producer/consumer patterns<br>	•	Eventual consistency<br>Setup<br>Two Spring Boot apps sharing one PostgreSQL database. Use existing local Kafka in Docker. Dockerize Spring Boot apps.<br>Architecture<br>text<br><br>Wallet Service (Spring Boot) --> Kafka (wallet_events) --> History Service (Spring Boot)<br>                              Shared PostgreSQL Database<br><br><br>Flow<br>	1	Client requests Wallet Service API.<br>	2	Wallet Service updates database immediately.<br>	3	Wallet Service publishes event to Kafka.<br>	4	History Service consumes event and updates history.<br>	5	Client queries history from History Service.<br>Process Flow<br>How Money Moves<br>text<br><br>Client Request<br>--> Wallet Service --> PostgreSQL<br>    [wallets: balance: $100, version: 2]<br>    [wallet_transactions: type: FUND, amount: $50]<br>--> Response (success)<br>--> Publish Event<br>--> Kafka<br>--> History Service<br>    [Event: {type: "FUNDED", transaction_events: {amount: 50, event_type: "WALLET_FUNDED", wallet_id: "abc-123", amount: "$50", event_data: {...}, created_at: timestamp}}]<br><br><br>Example: Transfer Transaction<br>Before Transfer:<br>	•	Wallet A: Balance $100<br>	•	Wallet B: Balance $50<br>During Transfer ($30 from A to B):<br>	1	Lock both wallets (ORDER BY id to prevent deadlock).<br>	2	Check A has >= $30.<br>	3	A.balance -= 30, B.balance += 30.<br>	4	Record both transactions.<br>	5	Publish event.<br>	6	Commit.<br>After Transfer:<br>	•	Wallet A: Balance $70<br>	•	Wallet B: Balance $80 Eventually:<br>	•	History Service: 2 events (A sent $30, B recv $30)<br>	•	Kafka Event: TRANSFER_DONE<br>Services<br>Wallet Service<br>	•	Create wallets for users.<br>	•	Add funds to wallets.<br>	•	Transfer money between wallets.<br>	•	Publish events.<br>History Service<br>	•	Listen for events from Kafka.<br>	•	Store transaction history.<br>	•	Provide history APIs.<br>	•	Handle duplicates gracefully.<br>Database Design<br>One PostgreSQL database with three tables:<br>sql<br><br>-- Wallet Service owns these<br>CREATE TABLE wallets (<br>  id VARCHAR(36) PRIMARY KEY,<br>  user_id VARCHAR(100) NOT NULL,<br>  balance DECIMAL(19,4) NOT NULL DEFAULT 0,<br>  version BIGINT NOT NULL DEFAULT 0,<br>  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,<br>  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP<br>);<br><br>CREATE TABLE wallet_transactions (<br>  id VARCHAR(36) PRIMARY KEY,<br>  wallet_id VARCHAR(36) NOT NULL,<br>  amount DECIMAL(19,4) NOT NULL,<br>  type VARCHAR(20) NOT NULL,  -- 'FUND', 'TRANSFER_OUT', 'TRANSFER_IN'<br>  status VARCHAR(20) NOT NULL,  -- 'COMPLETED', 'FAILED'<br>  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,<br>  FOREIGN KEY (wallet_id) REFERENCES wallets(id)<br>);<br><br>-- History Service owns this<br>CREATE TABLE transaction_events (<br>  id VARCHAR(36) PRIMARY KEY,<br>  wallet_id VARCHAR(36) NOT NULL,<br>  user_id VARCHAR(100) NOT NULL,<br>  amount DECIMAL(19,4) NOT NULL,<br>  event_type VARCHAR(30) NOT NULL,<br>  transaction_id VARCHAR(36),<br>  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,<br>  event_data JSONB<br>);<br><br><br>API Endpoints<br>Wallet Service<br>	•	POST /wallets - Create wallet for userId.<br>	•	POST /wallets/{walletId}/fund - Add money.<br>	•	POST /wallets/{walletId}/transfer - Send money to another wallet.<br>	•	GET /wallets/{walletId} - Check balance.<br>	•	GET /users/{userId}/wallets - List user's wallets.<br>History Service<br>	•	GET /wallets/{walletId}/history - Transaction history.<br>	•	GET /users/{userId}/activity - All user activity.<br>Core Operations<br>	1	Create wallet: Insert into PostgreSQL + publish event.<br>	2	Fund wallet: Update balance with optimistic locking + publish event.<br>	3	Transfer money: Update two wallets + publish event.<br>	4	Consume events: Process Kafka events into history table.<br>	5	Query history: Read from event-sourced history.<br>Key Learning Scenarios<br>PostgreSQL<br>	•	Handle concurrent updates without races.<br>	•	Use DECIMAL for money (no floats).<br>	•	Manage DB + Kafka transactions.<br>	•	Optimistic locking via version fields.<br>Kafka<br>	•	Producers handle failures.<br>	•	Proper consumer groups.<br>	•	Handle duplicates.<br>	•	Robust event schemas.<br>Integration<br>	•	Eventual consistency.<br>	•	Handle Kafka downtime with PostgreSQL up.<br>	•	Retry failures.<br>	•	Correlate events.<br>Business Rules<br>	•	Users: String IDs (no auth).<br>	•	Balances non-negative.<br>	•	Money: 4 decimal places.<br>	•	Balance updates immediate.<br>	•	History eventual.<br>	•	All auditable.<br>Event Design<br>Events:<br>json<br><br>{<br>  "eventType": "WALLET_FUNDED",<br>  "walletId": "wallet-123",<br>  "userId": "user-456",<br>  "amount": "100.00",<br>  "transactionId": "txn-789",<br>  "timestamp": "2025-08-19T10:30:00Z"<br>}<br><br><br>Types:<br>	•	WALLET_CREATED<br>	•	WALLET_FUNDED<br>	•	TRANSFER_COMPLETED<br>	•	TRANSFER_FAILED<br>Tech Stack<br>	•	Backend: Java + Spring Boot<br>	•	Database: PostgreSQL + Spring Data JPA<br>	•	Messaging: Apache Kafka<br>	•	Infrastructure: Docker Compose<br>	•	Testing: Integration tests spanning services<br>Success Criteria<br>	•	Concurrent funding without loss.<br>	•	Reliable event flow.<br>	•	History catches up on restarts.<br>	•	Understand optimistic locking for finance.<br>	•	Explain eventual consistency trade-offs.<br>	•	Goal: Understand PostgreSQL-Kafka in distributed systems, not production code.<br>Implementation Guide<br>Step 1: Project Setup<br>Create two Maven projects: wallet-service and history-service.<br>	•	Use Spring Initializr: Java 17+, Spring Boot 3.3+.<br>	•	Dependencies (both): Spring Web, Spring Data JPA, PostgreSQL Driver, Lombok.<br>	•	Wallet: Add Spring Kafka.<br>	•	History: Add Spring Kafka.<br>Step 2: Docker Setup<br>Use Docker Compose for apps, PostgreSQL; link to existing Kafka.<br>docker-compose.yml:<br>yaml<br><br>version: '3'<br>services:<br>  postgres:<br>    image: postgres:16<br>    environment:<br>      POSTGRES_DB: walletdb<br>      POSTGRES_USER: user<br>      POSTGRES_PASSWORD: pass<br>    ports:<br>      - "5432:5432"<br>  wallet-service:<br>    build: ./wallet-service<br>    depends_on:<br>      - postgres<br>    environment:<br>      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/walletdb<br>      SPRING_DATASOURCE_USERNAME: user<br>      SPRING_DATASOURCE_PASSWORD: pass<br>      SPRING_KAFKA_BOOTSTRAP_SERVERS: your-kafka-host:9092  # Link to local Kafka<br>    ports:<br>      - "8080:8080"<br>  history-service:<br>    build: ./history-service<br>    depends_on:<br>      - postgres<br>    environment:<br>      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/walletdb<br>      SPRING_DATASOURCE_USERNAME: user<br>      SPRING_DATASOURCE_PASSWORD: pass<br>      SPRING_KAFKA_BOOTSTRAP_SERVERS: your-kafka-host:9092<br>    ports:<br>      - "8081:8081"<br><br><br>For each service, add Dockerfile:<br>dockerfile<br><br>FROM openjdk:17-jdk-slim<br>COPY target/*.jar app.jar<br>ENTRYPOINT ["java", "-jar", "/app.jar"]<br><br><br>Build: mvn clean package, then docker-compose up.<br>Step 3: Database Entities<br>In both services, create JPA entities matching DB design.<br>	•	Wallets: @Entity, @Id String id = UUID.randomUUID().toString(), BigDecimal balance, long version.<br>	•	WalletTransactions: Similar.<br>	•	TransactionEvents: In History only.<br>Use @Version on version field for optimistic locking.<br>Step 4: Wallet Service<br>	•	Repositories: JpaRepository for Wallets, WalletTransactions.<br>	•	Services: WalletService with methods:<br>	◦	createWallet(String userId): Insert Wallet, publish WALLET_CREATED.<br>	◦	fundWallet(String walletId, BigDecimal amount): Find wallet, check version, update balance/version, insert transaction (FUND, COMPLETED), publish WALLET_FUNDED. Use @Transactional.<br>	◦	transfer(String fromId, String toId, BigDecimal amount): @Transactional, lock both (SELECT FOR UPDATE ORDER BY id), check from balance, update both balances/versions, insert two transactions (TRANSFER_OUT, TRANSFER_IN), publish TRANSFER_COMPLETED.<br>	•	Controllers: REST for APIs.<br>	•	Kafka: KafkaTemplate<String, String> for publishing JSON events to "wallet_events". Use ObjectMapper for serialization. Enable idempotence: producer.properties acks=all, enable.idempotence=true, retries=Integer.MAX_VALUE.<br>Step 5: History Service<br>	•	Repository: JpaRepository for TransactionEvents.<br>	•	Kafka Listener: @KafkaListener(topics = "wallet_events", groupId = "history-group").<br>	•	Consume: Parse JSON, check for duplicates (idempotency via id or transaction_id), insert TransactionEvents.<br>	•	Enable at-least-once: auto.offset.reset=earliest, enable.auto.commit=false, ack after insert.<br>	•	Controllers: REST for history queries (findByWalletId, findByUserId).<br>Step 6: Robustness<br>	•	Optimistic locking: Handle OptimisticLockException, retry or fail.<br>	•	Duplicates: History checks if event id exists before insert.<br>	•	Failures: Producers retry on transient errors. Consumers manual ack after success.<br>	•	Kafka down: Wallet continues DB updates; events queue when up.<br>	•	Testing: Integration tests with Testcontainers for PostgreSQL/Kafka, or embedded. Test concurrent funds/transfers.<br>Step 7: Run and Test<br>	•	Run Docker Compose.<br>	•	Use Postman for APIs.<br>	•	Simulate concurrency with JMeter.<br>	•	Restart services to check eventual consistency.</p>
